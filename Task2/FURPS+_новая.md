# Задание 2. FURPS+ — MVP онлайн-заявки на депозит

**Контур.** Банк «Стандарт», цифровизация депозитов: сайт (новый клиент) и интернет-банк (действующий клиент). Обработка заявки в MVP — вручную в бэк-офисе, учёт условий — в АБС.

**Что считаем архитектурно-значимым.** Требование влияет на границы систем, способ интеграции, размещение данных, стек или контур отказоустойчивости. Если его проигнорировать, решение придётся переделывать. Обычные пожелания к тексту кнопок в таблицу не входят.

**Как читать «Комментарий».** Источник (задание / IT-ландшафт) и *почему это бьёт по архитектуре*. Если требование добавлено сверх формулировок бизнеса — в комментарии есть пометка **[доп.]** и обоснование.

| Код | Требования | Комментарий |
|-----|------------------------------------|--------------|
| F | **Функциональные (Functionality)** | |
| F1 | На сайте новый клиент видит каталог доступных депозитов с **актуальными** ставками. | Каталог нельзя читать из Excel по почте (as-is, задание 1). Нужен онлайн-источник ставок, общий с интернет-банком. Иначе два канала покажут разные цифры. |
| F2 | С сайта клиент подаёт заявку: Ф. И. О. и номер телефона. | Сайт сегодня только витрина (PHP + React). Появляется контур приёма ПДн и передачи заявки дальше — это новый интеграционный шов, не «форма на PHP». |
| F3 | После заявки с сайта менеджер **кол-центра банка** видит её в системе КЦ, звонит клиенту и может предложить особые условия. | Система КЦ — React + Java Spring Boot + PostgreSQL, микросервисы подрядчика, в банке есть Java-экспертиза в команде АБС. Партнёрский КЦ в MVP не закладываем: у него нет доступа к заявкам с сайта и нет своего контура в инфраструктуре банка. |
| F4 | Новый клиент после звонка **приходит в отделение** на идентификацию. Сайт не открывает депозит и не заводит клиента дистанционно. | Регуляторное ограничение из задания. Архитектура сайта — только lead + КЦ, не онлайн-онбординг и не проводка в АБС. |
| F5 | В интернет-банке клиент видит каталог депозитов: базовые актуальные ставки и **персональные** ставки. | Персонализация требует идентификатора клиента и отдельного правила расчёта, не публичной витрины сайта. Источник ставок должен уметь отдавать и «общую», и «личную» цену. |
| F6 | В интернет-банке клиент выбирает счёт списания и сумму, подаёт заявку на открытие депозита, подтверждает операцию **СМС-кодом**. | Подтверждение — часть доверенного контура. Ядро ИБ (платформа подрядчика) уже умеет СМС, но его лучше не трогать (см. S3). Значит, нужен свой сценарий поверх существующего СМС-шлюза банка. |
| F7 | **MVP:** заявку обрабатывает менеджер бэк-офиса депозитов; он подтверждает условия депозита **в АБС**. | Цель на год — автооткрытие без бэк-офиса; MVP сохраняет человеческое согласование. Архитектура должна отделить «заявку в канале» от «учёта в АБС», чтобы потом убрать человека, не ломая каналы. |
| F8 | Клиент получает СМС: (1) после подтверждения размера ставки; (2) после открытия депозита. | События жизненного цикла заявки → СМС-шлюз банка → телеком. Это отдельный исходящий контур, не экран ИБ. |
| F9 | Ставки и процесс согласования ставки по заявке ведутся **в информационной системе**, а не в XLS. Ими пользуются бэк-офис депозитов **и** бэк-офис кредитов. | Сейчас ставки нигде, кроме Excel; расчёт и почта — узкое место as-is. Без системы ставок F1/F5 невыполнимы. Кандидат «положить в АБС» конфликтует с перегрузкой БД АБС (R3, P4) — решение по размещению в +R3. |
| F10 | **[доп.]** Заявка с сайта и из ИБ имеет единый статусный цикл (принята → в работе КЦ/бэка → ставка подтверждена → открыта / отказ) и **идемпотентность**: повторная отправка не создаёт дубль. | Иначе при ретраях, двойном клике и двух каналах появятся двойные звонки и двойные открытия. Нужен канонический объект «заявка» вне АБС. |
| F11 | **[доп.]** Каналы (сайт, ИБ) **не выполняют** бухгалтерское открытие вклада. Проводка и договор — только АБС (в MVP — после действий бэк-офиса; для нового клиента — после идентификации в отделении). | Защищает ядро учёта. Согласуется с запретом прямой работы ИБ с API АБС в новом процессе. |
| F12 | Трафик сайта и интернет-банка с чувствительными данными защищается **шифрованием канала** (TLS). | ПДн и реквизиты счетов. Требование безопасности в FURPS относят к Functionality. Минимальный уровень — HTTPS на обоих каналах; детали — F13. |
| F13 | **[доп.]** Заявки с сайта (ФИО, телефон) хранятся и передаются как персональные данные: доступ по ролям (КЦ, бэк-офис), журнал доступа, без выгрузки в почту и Excel. | **[доп.]** Задание говорит только про шифрование трафика. Для банка этого мало: as-is как раз ходит почта. Иначе «цифровая» заявка повторит текущую дыру. Ориентир — 152-ФЗ. |
| U | **Удобство использования (Usability)** | |
| U1 | Клиентский интерфейс сайта и ИБ — максимально понятный сценарий «увидел ставку → оставил заявку / открыл». | Бизнес-цель: привлечь более молодую аудиторию; сейчас онлайн почти не пользуются. Не усложнять MVP лишними шагами (кредит, полный онбординг). |
| U2 | Экраны депозитов следуют **принятой в банке дизайн-системе**: привычные цвета и брендированные элементы. | Одинаковые компоненты на сайте (React) и в ИБ (ASP.NET MVC) — иначе два визуальных контура и двойная стоимость сопровождения. |
| U3 | **[доп.]** Клиент в любой момент видит понятный статус заявки и следующее действие («ждите звонка», «придите в отделение», «подтвердите СМС», «депозит открыт»). | **[доп.]** Без статуса КЦ и бэк станут единственным «интерфейсом», вырастет нагрузка на звонки. Для ИБ статус читается из контура заявок, не из АБС. |
| R | **Надёжность (Reliability)** | |
| R1 | Целевая доступность сервисов нового процесса и каналов — **24/7, 99,9%** (недоступность порядка ~8,8 ч в год). | Требование бизнеса. Сейчас ИБ: мало клиентов, один ЦОД, одна группа серверов; команда ИБ считает 99,9% невыполнимым. Для архитектуры это **цель to-be**, а не обещание MVP на текущем монолите. Разрыв снимаем R2 и +R1. |
| R2 | При сбое основного ЦОД сервисы интернет-банка (и новый контур депозитов) остаются доступны за счёт **резервного ЦОД** и выдерживают расчётную нагрузку. | Резервный ЦОД уже есть, но активного распределения нет. Нужны репликация данных заявок/ставок и план переключения, а не «холодный» сервер без данных. |
| R3 | Онлайн-поток заявок **не ставит под угрозу работоспособность банка**. БД АБС уже перегружена; новый процесс не должен добавлять ей онлайн-нагрузки с каналов. | Ключевой риск. Отсюда: не читать каталог и не писать заявку синхронно в Oracle АБС; не размножать прямые интеграции «как платежи ИБ → БД АБС». |
| R4 | **[доп.]** Подача заявки на сайте и в ИБ успешна, даже если АБС или КЦ временно недоступны: заявка сохраняется в своём контуре и доставляется позже. | **[доп.]** Следствие R3 и запрета прямого API АБС. Канал должен быть автономным: очередь/буфер, а не синхронный двухфазный commit с АБС. |
| R5 | **[доп.]** Сбой СМС-шлюза не теряет факт «ставка подтверждена / депозит открыт»: уведомление повторяется; клиент видит статус в канале. | **[доп.]** СМС — внешний оператор. Надёжность процесса не должна равняться доставке одной SMS. |
| P | **Производительность (Performance)** | |
| P1 | Отклик клиентских операций в канале — **максимально быстрый** (ориентир бизнеса — миллисекунды на интерактив). | Формулировка бизнеса завышена для цепочки «ИБ → очередь → АБС → СМС». Архитектурно разделяем: **интерактив** (каталог, форма) — сотни мс из кэша/своей БД; **подтверждение и открытие** — асинхронно, клиент не ждёт АБС. |
| P2 | Загрузка справочных данных при платежах в ИБ сейчас **> 1 с**; это нужно устранить (кэш, не живой запрос в АБС). | Не депозитный сценарий, но тот же корень: ИБ ходит в БД АБС напрямую. Исправлять тем же приёмом, что и каталог депозитов, иначе новый процесс повторит антипаттерн. |
| P3 | Новые компоненты выдерживают рост заявок за счёт **горизонтального** масштабирования и распределения запросов между серверами, приложениями и ЦОД. | Балансировка и несколько инстансов. Не распространяется на АБС (P4). |
| P4 | АБС масштабируется **только вертикально** (Oracle, логика в PL/SQL). Нагрузку нового процесса на АБС ограничиваем и сглаживаем. | Нельзя «просто добавить серверов АБС». Подтверждение бэк-офисом — пакетно/по очереди, с лимитом, не шторм из каналов. |
| P5 | **[доп.]** Каталог ставок для витрины отдаётся из кэша/реплики; персональная ставка — отдельный короткий запрос, не полный пересчёт Excel-модели на каждый хит. | **[доп.]** Иначе F1/F5 и P1 несовместимы при пике с сайта. |
| S | **Поддерживаемость (Supportability)** | |
| S1 | В доработках **по возможности используем стек, который уже есть**: MS SQL и Oracle; языки, по которым в банке есть люди (.NET, PHP, Java, PL/SQL). | Снижает риск вендора и найма. Новые СУБД/языки — только если совместимы с текущими платформами разработки и есть хотя бы языковая экспертиза. |
| S2 | Новые технологии совместимы с платформами разработки банка (сайт PHP/React, ИБ .NET Framework 4.5 / ASP.NET MVC, АБС Delphi + Oracle, КЦ Java/Spring). | ИБ — монолит подрядчика на устаревшем .NET 4.5. Нельзя заложить в тот же процесс компонент, который эта платформа «не переварит». |
| S3 | Подтверждение СМС и депозитный функционал в ИБ делаем **силами команды банка**, **без доработки ядра** платформы подрядчиком. | Ядро обновляет подрядчик (10 человек снаружи). Зависимость сорвёт сроки MVP. СМС-шлюз уже сопровождает IT банка. |
| S4 | Если нужна очередь — **целевой** брокер **Kafka** (на вырост). Текущая платформа ИБ с Kafka **несовместима**. | Не встраивать Kafka в монолит 4.5. Вынести новый контур депозитов (см. S5) и стыковать брокер там; либо на MVP — совместимый с .NET буфер (например таблица MS SQL) с заделом под Kafka. |
| S5 | Допускается перевод интернет-банка на **микросервисы только в рамках открытия депозитов**, не всего монолита. | Локальный шов: модуль/сервис заявок и ставок рядом с монолитом, а не «переписать ИБ». Это же снимает S3 и S4. |
| S6 | Нужна документация, достаточная для **дальнейшего расширения** (кредиты онлайн, автооткрытие без бэка через год). | Контракты API, статусы заявки, схема интеграций, ADR по АБС/Kafka/ЦОД. Иначе следующий продукт повторит нелегальные интеграции. |
| S7 | **[доп.]** Ставки и согласование доступны сотрудникам депозитов и кредитов через штатный интерфейс (АБС или отдельное приложение), с историей изменений. | **[доп.]** Снимает Excel+почту. Нужно для сопровождения: кто поменял ставку и когда. |
| +R | **+ Ограничения (Restrictions)** | |
| +R1 | Требование 99,9% / два ЦОД **не блокирует** поставку MVP: фиксируем поэтапность (сначала контур заявок, затем активный резерв ИБ). Текущий ИБ остаётся на одной группе серверов до выделенного этапа. | Снимает конфликт «бизнес хочет 99,9%, команда ИБ не может». Иначе либо срыв сроков, либо фиктивное SLA. |
| +R2 | В **новом** процессе интернет-банк **не работает напрямую** с API (и тем более с БД) АБС. | Прямой доступ ИБ к БД АБС уже есть для платежей — его не расширяем. Связь только через буфер/сервис заявок; в АБС пишет бэк-офис (MVP) или контролируемый адаптер. |
| +R3 | **[доп.]** Справочник ставок и очередь заявок **не размещаем в перегруженной БД АБС**. Предпочтение: MS SQL (как у ИБ) или отдельный сервис; в АБС — только факт согласованных условий и открытие вклада. | **[доп.]** Бизнес предлагает «сделать ставки в АБС». Это удобно для бэка (один десктоп Delphi), но противоречит R3/P4. Компромисс: учёт в АБС, витрина и заявки — снаружи. |
| +R4 | **[доп.]** Не использовать партнёрский кол-центр для разбора заявок с сайта в MVP. | **[доп.]** Внешняя система, другие скрипты, нет контура ПДн банка. Масштаб — позже, отдельным договором и интеграцией. |
| +R5 | **[доп.]** Юридическое: дистанционно нельзя принять нового клиента без личной проверки документов. Архитектура сайта это не обходит. | Повтор F4 как constraint: никакого «открыли вклад с лендинга». |
| +R6 | **[доп.]** Физически ориентируемся на два существующих ЦОД; АБС не обязана быть активна в обоих для подачи заявки. | Заявка живёт в канальном контуре. Открытие вклада пережидает доступность АБС. |

## На что опираться в решении (кратко)

1. **Два канала — одна модель заявки и ставок**, не Excel и не копия логики в PHP и в .NET.
2. **АБС остаётся системой учёта**, не фронтом онлайн-нагрузки.
3. **Новый контур рядом с монолитом ИБ** (команда банка, свой стор, очередь с заделом под Kafka), без доработки ядра подрядчика.
4. **99,9% и второй ЦОД** — целевые ограничения to-be, не условие старта MVP.
5. **Сайт = лид + КЦ + визит в отделение**; **ИБ = заявка действующего клиента + СМС + бэк в АБС**.
