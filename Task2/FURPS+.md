# Архитектурно-значимые требования к MVP (FURPS+)

**Проект:** Банк «Стандарт» — цифровизация процесса открытия депозитов (MVP).  
**Цель:** Запуск онлайн-заявки на открытие депозита через сайт (для новых клиентов) и через интернет-банк (для действующих клиентов) с минимизацией ручных операций и сохранением стабильности учетной системы (АБС).

---

## Таблица требований FURPS+

| Код | Требование | Архитектурное обоснование / комментарий |
| :--- | :--- | :--- |
| **F** | **Функциональность (Functionality)** | |
| **F1** | На сайте новый клиент видит витрину депозитов с актуальными базовыми ставками. | Ставки должны отдаваться из единого онлайн-источника (сервиса ставок), а не из Excel-файлов, чтобы исключить расхождение данных между сайтом и интернет-банком. |
| **F2** | С сайта клиент может отправить заявку (лид), указав ФИО и номер телефона. | Сайт перестает быть только статичной витриной. Появляется контур сбора и первичной обработки персональных данных (ПДн) с передачей в банк. |
| **F3** | Заявка с сайта поступает операторам кол-центра банка для звонка клиенту и согласования условий. | Интеграция с системой кол-центра банка (Spring Boot + PostgreSQL). В MVP заявки с сайта передаются только во внутренний КЦ банка (партнерский КЦ не подключается из-за ограничений по ПДн). |
| **F4** | После консультации новый клиент посещает отделение банка для очной идентификации и подписания договора. | Регуляторное ограничение (115-ФЗ): дистанционное открытие первого счета новому клиенту без очной идентификации в MVP не реализуется. |
| **F5** | В интернет-банке действующий клиент видит каталог базовых и персональных ставок. | Требуется отдельный расчет персональной ставки по идентификатору клиента на основе истории и профиля в банке. |
| **F6** | В интернет-банке клиент выбирает продукт, счет списания, сумму и подтверждает открытие депозита СМС-кодом (OTP). | Реализация сценария двухфакторного подтверждения через существующий СМС-шлюз банка силами команды банка, без модификации закрытого ядра интернет-банка. |
| **F7** | На этапе MVP заявка из интернет-банка проверяется и подтверждается сотрудником бэк-офиса депозитов в АБС. | Переходный этап: процесс отделяет подачу заявки в канале от проведения операции в АБС, что позволяет через год перейти к автоматическому открытию без изменения каналов. |
| **F8** | Клиент получает СМС-уведомления об изменении статуса заявки (подтверждение ставки, успешное открытие вклада). | Асинхронная отправка системных событий через СМС-шлюз банка операторам связи. |
| **F9** | Базовые и специальные ставки ведутся сотрудниками депозитов и кредитов в информационной системе (веб-интерфейсе), а не в Excel. | Замена ручного расчета и рассылок по email единым реестром ставок с версионированием и журналом изменений. |
| **F10** | Заявки имеют единую статусную модель и поддерживают идемпотентность. | Исключение дублирования заявок и повторных списаний/звонков при сетевых сбоях и повторных кликах пользователя. |
| **F11** | Каналы (сайт, интернет-банк) не выполняют прямые финансовые проводки. Бухгалтерский учет и открытие договора ведутся исключительно в АБС. | Защита контура бухгалтерского учета и разграничение ответственности между витринами и учетной системой. |
| **F12** | Защита клиентского трафика и персональных данных (TLS, шифрование, ролевой доступ, аудит). | Соблюдение требований безопасности и 152-ФЗ при передаче и хранении данных клиентов. |
| **U** | **Удобство использования (Usability)** | |
| **U1** | Интуитивно понятный клиентский путь: минимум шагов от просмотра ставки до подачи заявки. | Снижение барьера входа для привлечения молодой аудитории и повышение конверсии в открытые депозиты. |
| **U2** | Использование единой дизайн-системы банка для интерфейсов сайта (React) и интернет-банка (ASP.NET). | Обеспечение узнаваемости бренда и снижения затрат на сопровождение фронтенд-компонентов. |
| **U3** | Прозрачное информирование клиента о текущем статусе заявки («Ожидайте звонка», «Подтвердите код», «Депозит открыт»). | Снижение нагрузки на телефонную линию кол-центра и повышение доверия клиентов к онлайн-процессу. |
| **R** | **Надежность (Reliability)** | |
| **R1** | Целевая доступность цифровых каналов 99.9% (24/7) с перспективой резервирования во втором ЦОД. | Долгосрочная цель бизнеса. На этапе MVP обеспечивается высокая доступность нового сервиса заявок, а монолит ИБ резервируется на следующем этапе. |
| **R2** | Изоляция АБС от пиковой онлайн-нагрузки каналов. | Прямые синхронные запросы из сайта и интернет-банка в перегруженную БД Oracle АБС запрещены. Все операции буферизуются. |
| **R3** | Автономность подачи заявок при временной недоступности АБС или КЦ. | Заявка сохраняется в локальной базе нового контура и отправляется в учетную систему асинхронно после восстановления связи. |
| **R4** | Гарантия обработки событий и повторная отправка при сбоях внешних сервисов (СМС-шлюз, телефония). | Использование очередей/буфера с механизмом повторных попыток (retry policy). |
| **P** | **Производительность (Performance)** | |
| **P1** | Мгновенный отклик витрины со ставками (кэширование базовых условий, время ответа < 200 мс). | Использование кэша базовых ставок для исключения повторных тяжелых расчетов при массовых просмотрах. |
| **P2** | Быстрый расчет персонализированной ставки в интернет-банке (отдельный легковесный запрос). | Оптимизация запроса персонализации без пересчета всей кредитно-депозитной модели банка. |
| **P3** | Горизонтальная масштабируемость новых клиентских сервисов и витрин. | Новые компоненты разворачиваются в нескольких экземплярах за балансировщиком нагрузки. |
| **P4** | Сглаживание и пакетирование потока задач, поступающих в АБС. | АБС масштабируется только вертикально; адаптер задач регулирует скорость передачи работы в АБС, защищая Oracle от шторма запросов. |
| **S** | **Поддерживаемость (Supportability)** | |
| **S1** | Использование существующего технологического стека банка (.NET, MS SQL, Java, PHP, Oracle PL/SQL). | Минимизация затрат на найм, обучение и внедрение новых инфраструктурных платформ. |
| **S2** | Разработка депозитного модуля ИБ силами внутренней команды банка без модификации ядра платформы подрядчика. | Монолит ИБ на .NET 4.5 обслуживается внешним подрядчиком. Доработка ядра несет высокие риски по срокам и стоимости, поэтому новый модуль встраивается как отдельный слой. |
| **S3** | Выделение отдельного микросервисного шва для депозитов рядом с монолитом интернет-банка. | Локальное внедрение микросервисной архитектуры только для нового процесса, без глобального переписывания всего монолита ИБ. |
| **S4** | Архитектурная готовность к переходу на брокер сообщений (Kafka) на горизонте 1 года. | На этапе MVP для интеграции используется transactional outbox (таблица в MS SQL), который в дальнейшем бесшовно заменяется на Kafka без изменения бизнес-логики. |
| **S5** | Ведение истории изменения ставок, аудит действий операторов и менеджеров. | Обеспечение прозрачности процессов ценообразования и выполнения требований регулятора. |
| **+** | **Ограничения (Constraints & Restrictions)** | |
| **+R1** | **Юридические**: обязательное очное присутствие нового клиента в отделении для открытия счета (115-ФЗ). | Сайт выполняет роль генератора лидов; открытие счета происходит в отделении. |
| **+R2** | **Технические**: запрет на расширение прямого доступа интернет-банка к БД АБС для депозитных операций. | Существующий прямой доступ ИБ в Oracle для платежей изолирован и не используется для нового функционала депозитов. |
| **+R3** | **Архитектурные**: запрет на хранение справочника ставок и очереди заявок в БД АБС (Oracle). | База данных АБС остается исключительно учетной системой. Все оперативные данные и очереди выносятся в MS SQL нового сервиса. |
| **+R4** | **Организационные**: исключение партнерского кол-центра из обработки заявок с персональными данными на этапе MVP. | Партнерский КЦ не имеет аттестованного контура ПДн и используется только для общих консультаций. |
| **+R5** | **Поэтапность**: запуск MVP за 6 месяцев с ручной обработкой бэк-офисом; автоматизация открытия без участия бэка — через 12 месяцев. | Разделение архитектурных слоев позволяет исключить ручной шаг в будущем без переделки каналов взаимодействия с клиентом. |
