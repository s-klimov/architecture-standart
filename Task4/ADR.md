# Архитектурное решение: Передача актуальных ставок в кол-центр банка и партнёрский кол-центр

### Метаданные
- **Название задачи:** Передача актуальных ставок по депозитам в кол-центр банка и партнёрский кол-центр
- **Автор:** Сергей Климов
- **Дата:** 30.08.2026
- **Статус:** Принято (Accepted)

## 1. Контекст и проблематика

Банк «Стандарт» готовится к запуску масштабной рекламной кампании розничных депозитов. Ожидается кратный рост обращений: как заявок через сайт и интернет-банк, так и входящих звонков от клиентов (включая консервативную и пожилую аудиторию, которая предпочитает звонить по телефону после просмотра рекламы).

**Проблемы As-Is в контексте кол-центров:**
- Операторы собственного КЦ банка (200 чел.) и партнёрского КЦ (100 чел.) консультируют клиентов по неактуальным данным из почты или устаревшим бумажным скриптам.
- Партнёрский кол-центр работает на внешней изолированной платформе и не имеет API-подключения к системам банка.
- Если во время рекламной кампании операторы кол-центров и сайт будут называть разные ставки, это вызовет негатив клиентов и финансовые риски банка.

**Цель решения:**
Обеспечить операторов собственного и партнёрского кол-центров актуальными базовыми ставками по депозитам синхронно с публикацией на сайте и в интернет-банке, соблюдая ограничения безопасности и технических возможностей систем.

## 2. Связь с архитектурным решением Задания 3

Настоящее решение является **расширением и дополнением** к `Task3/ADR.md`.
- Базовый справочник ставок уже вынесен в **«Контур заявок и ставок»** (.NET + MS SQL), где он версионируется и кэшируется.
- База данных АБС (Oracle) освобождена от роли витрины ставок и не участвует в онлайн-консультациях.
- В рамках данного кейса уточняется только способ доставки ставок в два кол-центра. Правило «партнёрский кол-центр не обрабатывает заявки с сайта и персональные данные» остается в силе.

## 4. Нефункциональные требования (NFR)

1. **NFR1 (Единый источник данных):** Все каналы (сайт, интернет-банк, КЦ банка, файл партнёра) получают базовые ставки из единого справочника Контура ставок.
2. **NFR2 (Разделение способов интеграции):**
   - Для КЦ банка (внутри периметра): синхронный REST API (HTTPS).
   - Для партнёрского КЦ (внешняя система без API): асинхронный файловый обмен (SFTP / каталог обмена).
3. **NFR3 (Безопасность и ПДн):** В файле для партнёра содержатся исключительно базовые публичные ставки. Персональные данные, индивидуальные спецставки и заявки клиентов партнёру не передаются.
4. **NFR4 (Свежесть данных):** После публикации ставки операторы КЦ банка видят изменения в течение 1–2 минут. Файл партнёру формируется сразу после публикации и дополнительно проверяется по расписанию (раз в час).
5. **NFR5 (Изоляция АБС):** Запросы ставок от кол-центров и файловый экспорт не создают никакой нагрузки на БД АБС (Oracle).
6. **NFR6 (Отказоустойчивость):** При временной недоступности сервиса ставок операторы КЦ банка видят закэшированные данные. При недоступности файлового канала партнёр использует последнюю валидную версию файла.

## 5. Архитектурное решение

Принято решение **не создавать второй справочник ставок и не открывать внешний сетевой API для партнёра**. Интеграция строится на двух специализированных швах:

1. **Для собственного кол-центра банка (онлайн REST API):**
   - Система КЦ банка (Spring Boot + PostgreSQL) встроена в корпоративную сеть банка.
   - В интерфейс оператора внедряется компактный UI-виджет актуальных ставок.
   - Сервис-адаптер КЦ запрашивает данные по HTTPS напрямую из сервиса каталога Контура ставок (из кэша).

2. **Для партнёрского кол-центра (файловый снимок через SFTP):**
   - В Контуре ставок реализуется легковесный компонент **«Экспортёр файлов»** (.NET).
   - При публикации новой версии ставок (или по таймеру) экспортёр формирует структурированный файл (CSV/XML) с контрольной суммой и выкладывает его на SFTP-сервер банка.
   - Партнёрский кол-центр настроенным фоновым процессом забирает файл, валидирует целостность по хэшу и загружает ставки в свою внутреннюю базу скриптов.

## 8. Рассмотренные альтернативы

### Альтернатива 1. Предоставление партнёрскому КЦ прямого доступа к REST API банка через VPN
- **Причина отклонения:** У партнёра нет технической готовности поддерживать синхронный API-клиент; требуется сложная аттестация безопасности внешнего периметра и длительное согласование сетевых доступов, что сорвет сроки запуска кампании.

### Альтернатива 2. Чтение ставок обоими кол-центрами напрямую из АБС
- **Причина отклонения:** Создает недопустимую нагрузку на БД Oracle АБС во время пика звонков; партнёр не имеет доступа к АБС; противоречит решениям Заданий 1–3.

### Альтернатива 3. Сохранение As-Is процесса (рассылка Excel-файлов по почте)
- **Причина отклонения:** Высокий риск человеческой ошибки, расхождение ставок между операторами и сайтом, отсутствие контроля версий и аудита во время масштабной рекламной кампании.

### Альтернатива 4. Перевод собственного КЦ банка на файловый обмен «для единообразия»
- **Причина отклонения:** Создает искусственную задержку в обновлении ставок для операторов банка; система КЦ банка уже находится во внутреннем контуре и легко интегрируется по REST API.

## 9. Риски и способы их минимизации

1. **Задержка доставки файла партнёру:**
   - *Риск:* В первые минуты после смены ставок оператор партнёра может называть старую ставку.
   - *Минимизация:* Экспорт формируется сразу по событию публикации; в скрипте оператора партнёра указывается дата/номер действующей редакции ставок.
2. **Повреждение или неполная загрузка файла партнёром:**
   - *Риск:* Ошибки в скриптах партнёра из-за сбоя парсинга.
   - *Минимизация:* Файл сопровождается контрольной суммой (хэш-файлом md5/sha256); при несовпадении хэша партнёр использует предыдущую валидную версию и сигнализирует об ошибке.
3. **Партнёр не забрал файл с SFTP:**
   - *Риск:* Ставки изменились, но партнёр продолжает работать по старым условиям.
   - *Минимизация:* Мониторинг каталога выгрузки службой IT банка с алертом в дежурную смену, если файл не вычитан в течение 30 минут.
