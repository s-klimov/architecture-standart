# Архитектурное решение: Концептуальная архитектура открытия депозитов (MVP)

### Метаданные
- **Название задачи:** Концептуальная архитектура онлайн-заявки и открытия депозитов (MVP)
- **Автор:** Сергей Климов
- **Дата:** 30.08.2026
- **Статус:** Принято (Accepted)

---

## 1. Контекст и проблематика

Банк «Стандарт» проводит цифровую трансформацию розничного бизнеса. В текущем состоянии (As-Is) процесс открытия депозитов имеет критические недостатки:
- Ставки рассчитываются вручную в Excel и рассылаются по электронной почте, из-за чего согласование занимает до часа, а данные часто рассинхронизируются.
- Открыть депозит можно только при личном визите в отделение с оформлением бумажного договора и сканированием его в АБС.
- Сайт банка работает только как информационная витрина, а интернет-банк (монолит на ASP.NET MVC 4.5) используется только для платежей и текущих счетов, напрямую обращаясь к базе данных АБС.
- Центральная учетная система АБС (Delphi + Oracle PL/SQL) испытывает высокую нагрузку на базу данных и масштабируется только вертикально. Прямое подключение новых онлайн-каналов к Oracle недопустимо.
- Монолит интернет-банка сопровождается сторонним подрядчиком; внесение изменений в ядро долго и дорого.

**Цель архитектурного решения на этапе MVP (срок 6 месяцев):**
1. Обеспечить онлайн-подачу заявки на депозит: для новых клиентов — через сайт (лид + звонок КЦ + визит в офис для идентификации), для действующих клиентов — через интернет-банк с подтверждением по СМС.
2. Внедрить единый электронный сервис ведения и публикации ставок вместо Excel и почты.
3. Разработать решение силами внутренней команды банка, не затрагивая закрытое ядро интернет-банка и защитив АБС от пиковой онлайн-нагрузки.
4. Заложить фундамент для перехода к полному автоматическому открытию депозитов без участия бэк-офиса на горизонте 1 года.

## 3. Нефункциональные требования (NFR)

1. **NFR1 (Безопасность и ПДн):** Все внешние и межсервисные каналы защищены протоколом TLS. Персональные данные (ФИО, телефон) хранятся с соблюдением требований 152-ФЗ, разграничением ролевого доступа и аудитом действий.
2. **NFR2 (Изоляция АБС):** Прямые синхронные обращения из каналов (сайт, интернет-банк) в БД Oracle АБС запрещены. Нагрузка на АБС сглаживается через асинхронный буфер задач.
3. **NFR3 (Отказоустойчивость):** При временной недоступности АБС или системы кол-центра заявки клиентов надежно сохраняются в базе данных сервиса заявок и обрабатываются после восстановления связи.
4. **NFR4 (Производительность):** Время отклика витрины каталога ставок не превышает 200 мс за счет кэширования базовых ставок. Время расчета персональной ставки — до 500 мс.
5. **NFR5 (Масштабируемость):** Сервис заявок и витрины каталога масштабируются горизонтально. Нагрузка на вертикально масштабируемую АБС строго контролируется адаптером.
6. **NFR6 (Стек и разработка):** Использование существующего технологического стека банка (.NET, MS SQL, Java, Oracle PL/SQL). Разработка нового функционала выполняется силами внутренней команды банка без привлечения подрядчика ядра интернет-банка.
7. **NFR7 (Архитектурный задел):** Архитектура готова к поэтапному переходу: замена таблицы Outbox на Kafka и подключение резервного ЦОД на горизонте 1 года.

## 4. Архитектурное решение

Принято решение **вынести управление ставками и жизненным циклом заявок в отдельный сервис «Контур заявок и ставок»**, расположенный рядом с монолитом интернет-банка, а АБС оставить исключительно системой бухгалтерского учета.

### 4.1. Архитектурные компоненты

#### 1. Контур заявок и ставок (новый компонент, стек .NET + MS SQL):
- **Сервис заявок и ставок:** REST API для создания и валидации заявок, проверки идемпотентности, управления статусами и расчета персональных ставок.
- **Рабочее место управления ставками:** простой веб-интерфейс для сотрудников депозитного и кредитного отделов (замена Excel и рассылок по email).
- **Кэш витрины:** оперативный кэш базовых ставок для быстрого ответа на запросы сайта и интернет-банка.
- **База данных контура (MS SQL):** хранение заявок, справочников ставок, журнала изменений и аудит-лога.
- **Исходящий буфер (Transactional Outbox):** таблица в MS SQL для гарантированной асинхронной доставки событий в систему КЦ, АБС и СМС-шлюз (на горизонте 1 года заменяется на Apache Kafka).

#### 2. Интернет-банк (ASP.NET MVC 4.5):
- **Модуль депозитов (новый слой):** набор страниц и контроллеров, разработанных внутренней командой банка. Общается с сервисом заявок по REST API.
- **Ядро интернет-банка (платформа подрядчика):** отвечает за авторизацию, отображение счетов и переводы. Код ядра не модифицируется.
- **База данных ИБ (MS SQL):** используется для существующих функций (сессии, платежи); депозитные заявки хранятся в БД нового контура.

#### 3. АБС (Delphi + Oracle PL/SQL):
- **Адаптер заявок (новый компонент, команда АБС):** сервис, который периодически вычитывает задачи из буфера контура заявок и передает их в обработку бэк-офису.
- **Рабочее место Delphi:** интерфейс для сотрудников отделений и бэк-офиса.
- **PL/SQL пакеты и БД Oracle:** проведение проводок, открытие лицевых счетов и учет депозитных договоров.

#### 4. Вспомогательные и внешние системы:
- **Сайт (PHP + React):** витрина базовых ставок + форма подачи заявки-лида, подключенные к REST API контура.
- **Система кол-центра банка (React + Spring Boot + PostgreSQL):** получение заявок с сайта через асинхронный адаптер, отображение карточки лида оператору.
- **СМС-шлюз банка:** генерация и проверка OTP-кодов, отправка сервисных уведомлений клиентам.

## 7. Рассмотренные альтернативы

### Альтернатива 1. Прямой доступ интернет-банка и сайта к БД АБС (Oracle)
- **Суть:** Расширить существующий подход интернет-банка (прямые вызовы процедур и чтение таблиц Oracle) на открытие депозитов и витрину сайта.
- **Причина отклонения:** БД АБС уже перегружена. Дополнительный поток онлайн-запросов приведет к сбоям в работе банка. Нарушается принцип изоляции учетного ядра.

### Альтернатива 2. Размещение справочника ставок и логики заявок внутри АБС
- **Суть:** Доработать АБС (Delphi/Oracle), чтобы она хранила ставки и отдавала их наружу.
- **Причина отклонения:** В АБС отсутствует API-шлюз для внешних каналов; Oracle масштабируется только вертикально; отделы депозитов и кредитов в АБС разделены и не имеют общего интерфейса.

### Альтернатива 3. Доработка закрытого ядра интернет-банка силами подрядчика и внедрение Kafka
- **Суть:** Заказать подрядчику переработку монолита ИБ (.NET 4.5) с интеграцией Kafka для связи с АБС.
- **Причина отклонения:** Высокий риск срыва сроков (6 месяцев), зависимость от внешнего релиза подрядчика, несовместимость устаревшей версии .NET 4.5 с актуальными библиотеками Kafka.

### Альтернатива 4. Полный дистанционный онбординг новых клиентов с сайта
- **Суть:** Открывать депозит новому клиенту сразу на сайте без визита в банк.
- **Причина отклонения:** Юридические ограничения (115-ФЗ) требуют очной идентификации клиента при первом открытии счета.

## 8. Ограничения, риски и компромиссы

1. **Ручная обработка заявок бэк-офисом в MVP:**
   - *Компромисс:* На этапе MVP сохраняется участие сотрудника бэк-офиса для подтверждения заявки в АБС.
   - *Минимизация:* Архитектура четко отделяет канальный слой от учетного. На горизонте 1 года шаг бэк-офиса заменяется автоматическим вызовом PL/SQL пакета без доработки сайта и интернет-банка.
2. **Использование Outbox-таблицы в MS SQL вместо брокера сообщений:**
   - *Компромисс:* Для снижения технологической сложности на старте используется таблица-буфер в MS SQL.
   - *Минимизация:* Контракты сообщений и логика обработки проектируются как слабосвязанные события, что позволит бесшовно переключить транспорт на Kafka на втором этапе.
3. **Существующий прямой доступ ИБ → АБС для платежей:**
   - *Риск:* Старый технический долг по платежам остается в системе.
   - *Минимизация:* Зафиксировано строгое архитектурное правило: новый функционал депозитов использует исключительно выделенный сервис заявок.
