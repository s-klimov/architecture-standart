### **Решение**

Принимаем решение: **вынести заявки и ставки в отдельный контур рядом с монолитом интернет-банка; АБС оставить системой учёта; каналы не открывают вклад.**

Это снимает конфликт «бизнес хочет онлайн-заявку, а АБС нельзя нагружать и нельзя отдать подрядчику ядро ИБ».

#### Какие команды участвуют

| Команда | Роль в MVP |
| :- | :- |
| Команда цифровой трансформации (10) | Контракты API, статусы заявки, границы систем, этот ADR. |
| Интернет-банк, команда банка (10) | Модуль депозитов в ИБ и сервис заявок/ставок на .NET. Ядро MVC 4.5 не меняют. |
| Интернет-банк, подрядчик (10) | **Не участвует** в MVP — иначе сроки упрутся в релиз ядра (S3). |
| Команда АБС (20) | Адаптер входящих задач, сценарий бэка в Delphi/PL-SQL, открытие вклада и проводка. Часть людей с Java помогает доработать КЦ. |
| Команда сайта | Витрина и форма лида на PHP + React, вызовы API контура. |
| Сопровождение КЦ (подрядчик, 5) | Карточка заявки с сайта, статусы для оператора. |
| IT банка / СМС-шлюз | OTP для ИБ и уведомления UC8. |
| Бэк-офис депозитов (бизнес) | Обрабатывает заявки в АБС по-старому, ставки ведёт в контуре. |
| Бэк-офис кредитов (бизнес) | Ведёт ставки в том же рабочем месте, без Excel. |
| Отделения (фронт) | Идентификация нового клиента и договор. |
| Партнёрский КЦ | Вне объёма. |

##### Комментарий к контексту

В центре не «весь банк», а контур MVP. Зелёный ящик — **новое**: единая модель заявки и ставок для сайта и ИБ. Оранжевый — АБС: договор и проводка. Жёлтый пунктир — телеком и партнёрский КЦ (второй не подключаем).

Стрелки сознательно разные: фиолетовые — человек, синие — синхронный HTTPS канала, зелёный пунктир — очередь. Так видно, что клиент не ходит в АБС, а АБС не торчит в интернет.

##### Комментарий к контейнерам

**Интернет-банк** режем на три части, чтобы не «переписать монолит»:

1. **Веб-приложение ИБ** — ядро подрядчика: логин, платежи, текущие счета. Существующий прямой доступ к БД АБС для платежей **не используем** для депозитов.
2. **Модуль депозитов** — экраны каталога, заявки, OTP, статуса. Пишет только команда банка, стыкуется с ядром как набор страниц, не как патч платформы.
3. **БД ИБ (MS SQL)** — как была: сессии и платежи. Заявки на депозит сюда не кладём, чтобы не смешать контуры и не упереться в ядро.

Рядом — **контур заявок и ставок** (это и есть «микросервис только для депозитов», S5):

- **Сервис заявок и ставок** — каноническая заявка, статусы, идемпотентность, персональная ставка.
- **Рабочее место ставок** — депозиты и кредиты вместо Excel и почты.
- **БД контура (MS SQL)** — заявки, ставки, журнал; не Oracle АБС.
- **Кэш витрины** — базовые ставки для сайта и ИБ.
- **Исходящий буфер (таблица MS SQL)** — лиды в КЦ, задачи в АБС, СМС. Позже ту же границу займёт Kafka, не монолит 4.5.

**АБС** детализируем так, чтобы было ясно, *куда* можно трогать легаси:

1. **Клиент Delphi** — отделение и бэк, как сейчас.
2. **Адаптер заявок (новый)** — забирает задачи из буфера, отдаёт работу бэку, возвращает статус. Каналы в адаптер по HTTPS не бьют.
3. **PL/SQL** — открытие вклада, проводки, сканы.
4. **Oracle** — только учёт согласованных условий и факт вклада. Справочник ставок и очередь заявок сюда не переезжают: иначе снова перегрузим единственную вертикальную БД.

#### Логика выбора

1. **Два канала — одна заявка и одни ставки.** Иначе сайт на PHP и ИБ на .NET снова разъедутся, как Excel и почта в задании 1.
2. **АБС — система учёта, не фронт онлайна.** Бизнес предлагал «положить ставки в АБС» — удобно бэку, вредно банку (R3, P4). Компромисс: витрина и заявка снаружи, факт вклада внутри.
3. **Новый контур рядом с ИБ, не внутри ядра.** Выполняет S3/S5 и даёт место очереди (S4) без Kafka в .NET 4.5.
4. **Сайт = лид + КЦ + визит; ИБ = заявка действующего клиента + СМС + бэк в АБС.** Это ровно промежуточная цель на 6 месяцев. Через год человека в UC7 убирают, каналы не переписывают.
5. **99,9% не обещаем на текущем монолите.** Иначе либо срыв MVP, либо фиктивное SLA.

### **Альтернативы**

**А1. Расширить прямой доступ интернет-банка к БД АБС** (как платежи и текущие счета).

Отклонено. Депозитный онлайн-поток ударит в уже перегруженный Oracle. Нарушает запрет новой прямой интеграции с API/БД АБС. Каталог и заявка станут недоступны вместе с АБС. Автооткрытие через год всё равно потребует вынести контур.

**А2. Хранить ставки и заявки в АБС (предложение бизнеса).**

Отклонено как место *онлайн-витрины*. Бэку привычен один Delphi, но это противоречит R3/P4/+R3. Кредиты и депозиты в АБС и так не видят данные друг друга — Excel от этого не умрёт, просто переедет в ту же узкую БД. В АБС остаётся только согласованный факт.

**А3. Доработать ядро ИБ силами подрядчика и сразу внедрить Kafka в монолит.**

Отклонено для MVP. Ядро обновляет внешняя команда из 10 человек; платформа 4.5 с Kafka несовместима. Срок и риск вендора выше ценности. Kafka оставляем целевым брокером *контура*, не монолита.

**А4. Открывать вклад с сайта без визита / подключить партнёрский КЦ.**

Отклонено. Нового клиента нельзя принять без проверки документов. У партнёрского КЦ нет контура ПДн банка и доступа к заявкам сайта.

**А5. Отдельный микросервисный ландшафт «с нуля» (новая СУБД, новый язык).**

Отклонено. Нет экспертизы и платформы разработки под третий стек. .NET + MS SQL рядом с ИБ и Java только там, где КЦ уже на Spring.

#### **Недостатки, ограничения, риски**

- **Человек в контуре.** MVP не сокращает операционку бэка: заявки из ИБ всё ещё обрабатывают вручную. Ценность — канал и чистый шов к году автоматизации, не мгновенная экономия FTE.
- **Два ЦОД и 99,9%.** На старте ИБ по-прежнему одна группа серверов. Если бизнес потребует SLA «с понедельника», нужно отдельное решение по активному резерву — это не этот ADR.
- **Буфер вместо Kafka.** Таблица-outbox проще оперировать команде .NET, но нет привычной для Kafka семантики потребителя. Риск: самописные ретраи. Снимаем контрактом адаптера и лимитом вычитки в АБС.
- **Адаптер АБС — новый шов на легаси.** Ошибка в PL/SQL или «шторм» без лимита снова ударит в Oracle. Нужны квота и идемпотентность на стороне адаптера.
- **Два визуальных стека.** Сайт на React, ИБ на MVC 4.5. Дизайн-система (U2) потребует дисциплины, иначе два UI.
- **КЦ на платформе подрядчика.** Карточка лида зависит от их релиза. Смягчение: в банке есть Java-экспертиза в команде АБС, объём — отображение заявки, не новая CRM.
- **Прямой доступ ИБ → БД АБС остаётся для платежей.** Мы его не расширяем, но и не закрываем. Риск: кто-то «для скорости» прочитает ставки тем же способом. Контроль — ревью и этот ADR.
- **Регуляторика.** Сайт никогда не становится каналом открытия вклада. Если продукт захочет дистанционный онбординг — это новый ADR и другая идентификация, не «допилить форму».
